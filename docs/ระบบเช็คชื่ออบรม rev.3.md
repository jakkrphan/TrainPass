# Prompt: ระบบลงทะเบียน + เช็คชื่อเข้าร่วมอบรม

สร้างเว็บแอประบบลงทะเบียน + เช็คชื่อเข้าร่วมอบรม โดยมี 3 ส่วนหลัก:

> **แก้ไขเพิ่มเติม (9 ต.ค. 2569)** — **ยกเลิก CAPTCHA (Cloudflare Turnstile)** บนหน้าลงทะเบียนสาธารณะ ไม่ใช้บริการกันบอทภายนอกแล้ว กันบอทด้วย honeypot + ตรวจเวลากรอกฟอร์ม + rate-limit ต่อ IP แทน (ดูข้อ 2)
>
> **หมายเหตุฉบับแก้ไข (rev. 3)** — เพิ่ม **โหมดการนับที่นั่ง 2 แบบ** (`per_day` แยกรายวัน กับ `whole_course` หลักสูตรต่อเนื่องนับที่นั่งรวมก้อนเดียว) ดูข้อ 0.1 ซึ่งเป็นตารางเปรียบเทียบกฎของทั้งสองโหมด ทุกหัวข้อที่พฤติกรรมต่างกันตามโหมดถูกระบุกำกับไว้แล้ว
>
> **หมายเหตุฉบับแก้ไข (rev. 2)** — ฉบับนี้ปรับจากฉบับแรกหลัง review พบว่า data model เดิมยังไม่รองรับสิ่งที่ feature สัญญาไว้ จุดที่เปลี่ยนสำคัญที่สุดคือ **ย้ายสถานะอนุมัติไปอยู่ที่ระดับ "วัน" (`RegistrantEventDay.status`)** เพราะที่นั่งจำกัดแยกรายวัน ส่วนที่เพิ่มใหม่ทั้งหมดทำเครื่องหมาย 🆕 ไว้

## 0) หลักการที่ต้องยึดทั้งระบบ (อ่านก่อนเริ่มเขียนโค้ด) 🆕

### 0.1 โหมดการนับที่นั่ง: แยกรายวัน หรือ รวมทั้งคอร์ส 🆕

ระบบต้องรองรับ **สองรูปแบบที่ต่างกันโดยสิ้นเชิง** เลือกได้ต่อโครงการผ่าน `Event.seatMode` และเลือกได้เฉพาะตอนสถานะ `draft` เท่านั้น:

| | **A. `per_day` — แยกที่นั่งรายวัน** (ค่าเริ่มต้น) | **B. `whole_course` — นับที่นั่งรวมทั้งคอร์ส** |
|---|---|---|
| ใช้กับ | หัวข้อเดียวจัดหลายรอบให้เลือก เช่น "อบรม IT Security จัด 3 รอบ เลือกมาวันไหนก็ได้" | หลักสูตรต่อเนื่องที่ต้องเรียนครบทุกวัน เช่น "อบรมพยาบาลเฉพาะทาง 5 วัน รับ 40 คน" |
| ที่นั่งเก็บที่ | `EventDay.maxSeats` แยกทุกวัน | `Event.maxSeats` ก้อนเดียว (`EventDay.maxSeats` ไม่ใช้/ซ่อนใน UI) |
| ผู้ลงทะเบียนเลือกวัน | เลือกเองได้หลายวันอิสระ ต้องเลือกอย่างน้อย 1 วัน | **เลือกไม่ได้** ระบบผูกให้ครบทุกวันอัตโนมัติ |
| หน่วยของการอนุมัติ | รายวัน (อนุมัติวันที่ 1 แต่วันที่ 6 เข้าคิวรอได้) | ทั้งคน ทั้งคอร์ส — อนุมัติ/ปฏิเสธ/ยกเลิกรายวันไม่ได้ |
| Waitlist | คิวแยกของแต่ละวัน | คิวเดียวของทั้งโครงการ |
| ตัวหารบนแดชบอร์ด | approved ของวันที่รอบนั้นผูกอยู่ | approved ทั้งโครงการ (เท่ากันทุกรอบ) |
| เกณฑ์ผ่านการอบรม | ไม่มี (มาวันไหนก็นับวันนั้น) | `attendanceThreshold` เช่น ต้องเช็คชื่อ ≥ 80% ของรอบทั้งหมดถึงถือว่าผ่าน |
| ตรวจ "ไม่ได้ลงวันนี้ไว้" ตอนเช็คชื่อ | จำเป็นมาก เป็นกรณีที่เกิดจริงบ่อย | แทบไม่เกิด เพราะทุกคนมีครบทุกวัน แต่ยังตรวจตามเดิม (กันข้อมูลเพี้ยน) |

**กฎเฉพาะของโหมด `whole_course` ที่ต้อง implement:**

- หน้า public **ไม่มี checkbox เลือกวัน** แสดงรายการวันทั้งหมดเป็นข้อมูลอย่างเดียว พร้อมข้อความชัดเจนว่า "หลักสูตรต่อเนื่อง ต้องเข้าร่วมครบทุกวัน" และแสดงที่นั่งคงเหลือเป็นตัวเลขเดียว เช่น "เหลือ 12 / 40 ที่นั่ง"
- ตอน submit ระบบสร้างแถว `RegistrantEventDay` ให้ **ทุกวันของโครงการ** อัตโนมัติ โดยทุกแถวมีสถานะเดียวกันเสมอ — แถวรายวันยังคงอยู่เพื่อให้ Check-in App, การนับยอด และรายงานรายวันใช้ตรรกะชุดเดียวกันทั้งสองโหมด ไม่ต้องเขียนโค้ดแยกสองชุด
- การเปลี่ยนสถานะทำเป็นก้อนเสมอ (อนุมัติ = อัปเดตทุกแถวเป็น `approved` ใน transaction เดียว) — UI ซ่อนปุ่มรายวัน และ **backend ต้อง reject** ถ้ามี request ขอเปลี่ยนสถานะเฉพาะบางวันในโหมดนี้
- ผู้ลงทะเบียนยกเลิกเองได้เฉพาะ "ยกเลิกทั้งหลักสูตร" ไม่มีตัวเลือกยกเลิกรายวัน
- `EventDay.isClosed` ไม่มีผลในโหมดนี้ (ปิดรับต้องปิดทั้งโครงการ)
- **เพิ่ม/ลบวันหลัง `published`** กระทบทุกคนพร้อมกัน: เพิ่มวันใหม่ → ระบบสร้างแถวรายวันให้ทุกคนที่ `pending`/`approved` อัตโนมัติ และต้องเตือนให้ผู้จัดส่ง broadcast แจ้งผู้เข้าอบรม; ลบวัน → ลบแถวของทุกคนและเตือนว่ากระทบประวัติเช็คชื่อของรอบที่ผูกวันนั้น
- **ห้ามสลับ `seatMode` หลังมีผู้ลงทะเบียนแล้ว** เพราะความหมายของที่นั่งและของแถวรายวันเปลี่ยนไปทั้งหมด — ล็อกค่าตั้งแต่กด publish ถ้าจำเป็นต้องเปลี่ยนจริงให้ clone เป็นโครงการใหม่แทน
- Clone โครงการต้องคัดลอก `seatMode`, `maxSeats` และ `attendanceThreshold` มาด้วย

### 0.2 สถานะอนุมัติอยู่ที่ระดับ "วัน" ไม่ใช่ระดับ "คน"

เนื่องจากแต่ละวันของโครงการมีที่นั่งจำกัดแยกกัน และผู้ลงทะเบียน 1 คนเลือกเข้าร่วมได้หลายวัน สถานะเดียวต่อคนจึงใช้ไม่ได้ เช่น คนเลือกวันที่ 1 (ว่าง) + วันที่ 6 (เต็ม) พร้อมกัน จะให้สถานะเดียวเป็นอะไรก็ผิดทั้งคู่

ดังนั้น:

- **`RegistrantEventDay.status`** คือสถานะจริงที่ระบบใช้ตัดสินใจทุกอย่าง (`pending | approved | rejected | waitlisted | cancelled`) — หนึ่งแถวต่อ 1 คน ต่อ 1 วัน
- **`Registrant.status`** เป็นเพียง **สถานะสรุป (derived)** ไว้ค้นหา/แสดงผลเร็ว ๆ คำนวณใหม่ทุกครั้งที่แถวรายวันเปลี่ยน ตามลำดับความสำคัญ: มี approved อย่างน้อย 1 วัน → `approved`; ไม่มี approved แต่มี pending → `pending`; ไม่มีทั้งคู่แต่มี waitlisted → `waitlisted`; ทุกวันถูกยกเลิก → `cancelled`; ทุกวันถูกปฏิเสธ → `rejected`
- การอนุมัติ/ปฏิเสธ/ยกเลิก/waitlist ทำได้ **รายวัน** เช่น อนุมัติวันที่ 1 แต่ให้วันที่ 6 อยู่ในคิวรอ — ⚠️ เฉพาะโหมด `per_day` เท่านั้น ส่วนโหมด `whole_course` ทุกแถวรายวันต้องเปลี่ยนสถานะพร้อมกันเสมอ (ดูข้อ 0.1)
- ปุ่ม "อนุมัติ" ในหน้ารายชื่อ = อนุมัติทุกวันที่ผู้ลงทะเบียนคนนั้นเลือกไว้และยังมีที่นั่ง วันที่เต็มให้เป็น `waitlisted` อัตโนมัติ พร้อมแจ้งผู้จัดใน UI ว่า "อนุมัติ 1 จาก 2 วัน (วันที่ 6 เต็ม → เข้าคิวรอ)"
- QR code ยังคงเป็น **1 รหัสต่อ 1 คนต่อ 1 โครงการ** (ไม่ได้แยกตามวัน) ตอนสแกนจึงต้องตรวจสองชั้นเสมอ: แถวรายวันของ "วันนั้น" ต้องมีอยู่จริง **และ** ต้องมีสถานะ `approved`

### 0.3 นิยาม "ที่นั่งคงเหลือ"

**โหมด `per_day` — นับรายวัน:**

```
seatsTaken(day)     = จำนวนแถว RegistrantEventDay ของวันนั้นที่ status ∈ {pending, approved}
seatsRemaining(day) = day.maxSeats - seatsTaken(day)   // ถ้า maxSeats เป็น null = ไม่จำกัด
```

**โหมด `whole_course` — นับทั้งโครงการ:** 🆕

```
seatsTaken(event)     = จำนวน "คน" (Registrant) ในโครงการที่ status ∈ {pending, approved}
seatsRemaining(event) = event.maxSeats - seatsTaken(event)
```

⚠️ จุดที่พลาดง่ายที่สุดของโหมดนี้คือไปนับแถว `RegistrantEventDay` เหมือนโหมดแรก ซึ่งจะทำให้คน 1 คนในคอร์ส 5 วันถูกนับเป็น 5 ที่นั่ง — ต้องนับที่ระดับ `Registrant` เท่านั้น (`COUNT(DISTINCT registrantId)` หรือนับจากตาราง Registrant ตรง ๆ)


- **นับ `pending` ด้วย** เพื่อกันคนลงทะเบียนเกินที่นั่งเป็นเท่าตัวในโหมด manual (ถ้าไม่นับ จะมีคน pending 300 คนสำหรับที่นั่ง 40 ที่ แล้วต้องปฏิเสธคนส่วนใหญ่ทีหลัง ซึ่งแย่กว่าบอกตั้งแต่แรกว่าเต็ม)
- `waitlisted`, `rejected`, `cancelled` **ไม่นับ** เป็นที่นั่งที่ถูกจอง
- **TTL ของ pending** 🆕: กำหนดค่าได้ต่อโครงการ (`pendingHoldHours`, ค่าเริ่มต้น null = ไม่หมดอายุ) ถ้าตั้งไว้ แถว pending ที่เกินเวลาจะถูกย้ายไป `waitlisted` อัตโนมัติโดย cron/scheduled job เพื่อคืนที่นั่งให้คิว
- หน้า public แสดงที่นั่งคงเหลือจากสูตรเดียวกันนี้เสมอ ห้ามคำนวณคนละสูตรกับตอน submit
- 🆕 เขียนเป็นฟังก์ชันเดียว `getSeatAvailability(event, dayIds)` ที่แตกตาม `seatMode` ข้างใน แล้วให้ทุกที่ (หน้า public, manual add, หน้าอนุมัติ, การเลื่อนคิว) เรียกตัวเดียวกัน ห้ามเขียนสูตรซ้ำในแต่ละหน้า

### 0.4 กัน race condition ตอนจองที่นั่ง

การ "เช็คแล้วค่อย insert" เฉย ๆ ไม่พอ สองคนกดพร้อมกันยังเกินได้ ต้องทำใน transaction เดียวและล็อกแถววันนั้นไว้:

```ts
await prisma.$transaction(async (tx) => {
  for (const dayId of selectedDayIds) {
    // ล็อกแถว EventDay กันคนอื่นนับพร้อมกัน (MySQL InnoDB)
    await tx.$executeRaw`SELECT id FROM EventDay WHERE id = ${dayId} FOR UPDATE`;
    const taken = await tx.registrantEventDay.count({
      where: { eventDayId: dayId, status: { in: ["pending", "approved"] } },
    });
    const day = await tx.eventDay.findUniqueOrThrow({ where: { id: dayId } });
    const full = day.maxSeats !== null && taken >= day.maxSeats;
    // full → status = "waitlisted", ไม่ full → "pending" หรือ "approved" ตาม event.autoApprove
  }
}, { isolationLevel: "ReadCommitted" });
```

🆕 **โหมด `whole_course` ล็อกคนละแถว** — ไม่ได้ล็อก `EventDay` ทีละวัน แต่ล็อกแถว `Event` แถวเดียว (`SELECT id FROM Event WHERE id = ? FOR UPDATE`) แล้วนับจำนวน `Registrant` ที่ status ∈ {pending, approved} เทียบกับ `event.maxSeats` ครั้งเดียว ถ้ายังพอ จึงสร้าง `Registrant` + แถว `RegistrantEventDay` ของทุกวันใน transaction เดียวกัน

ทางเลือกที่เบากว่า: เก็บ counter `seatsTaken` ไว้ใน `EventDay` แล้วใช้ conditional update (`UPDATE EventDay SET seatsTaken = seatsTaken + 1 WHERE id = ? AND (maxSeats IS NULL OR seatsTaken < maxSeats)`) แล้วดู affected rows — เลือกทางใดทางหนึ่งแล้วใช้ให้เหมือนกันทั้งระบบ (auto-approve, manual submit, manual add, waitlist promote)

### 0.5 Timezone และรูปแบบวันที่ 🆕

- เก็บทุก `DateTime` เป็น UTC ในฐานข้อมูล แสดงผลเป็น **Asia/Bangkok** เสมอ
- `EventDay.date` เก็บเป็น **`@db.Date`** (ไม่ใช่ `DateTime`) เพราะเป็น "วัน" ไม่ใช่ "เวลา" — ถ้าเก็บเป็น DateTime แล้วเวลาต่างกันไม่กี่วินาที `@@unique([eventId, date])` จะกันวันซ้ำไม่ได้
- แสดงปีเป็น **พ.ศ.** ในทุกหน้าที่ผู้ใช้เห็น (หน้า public, อีเมล, ตั๋ว, รายงาน) แต่เก็บเป็น ค.ศ. ในฐานข้อมูล

## 1) ORGANIZER PORTAL (ต้อง login)

- แสดงรายการโครงการเฉพาะที่ user คนนั้นเกี่ยวข้องเท่านั้น คือ:
  - (a) เป็นเจ้าของโครงการ (owner) หรือ
  - (b) ถูกเพิ่มชื่อเป็นผู้ร่วมจัด (collaborator) ในโครงการนั้น

  ห้ามดึงโครงการทั้งหมดในระบบมาแสดง ต้อง filter ที่ query ฝั่ง backend เสมอ
- **บทบาท `admin` (สิทธิ์ระดับระบบ แยกจาก owner/collaborator ของแต่ละโครงการ)**: ผู้ใช้ที่ `User.role = "admin"` เห็น**ทุกโครงการในระบบ**ได้โดยไม่ต้องเป็น owner หรือถูกเพิ่มเป็น collaborator (ข้อยกเว้นเดียวของกฎ filter ด้านบน) และจัดการบัญชีผู้ใช้อื่นได้ (เปลี่ยน role, ปิดการใช้งานบัญชี) แต่**ยังต้องผ่าน audit/log ทุกครั้งที่เข้าไปแก้ไขโครงการที่ตัวเองไม่ได้เป็น owner** เพื่อให้ตรวจสอบย้อนหลังได้ว่า admin เข้าไปทำอะไรในโครงการของคนอื่นบ้าง — สิทธิ์นี้มีไว้สำหรับดูแลระบบ/แก้ปัญหาเท่านั้น ไม่ใช่สิทธิ์ที่มอบให้ผู้จัดทั่วไป
  - 🆕 บันทึกลงตาราง `AuditLog` (ดู data model) ทุกครั้งที่ actor ไม่ได้เป็น owner/collaborator ของโครงการนั้น และทุกครั้งที่มีการเปลี่ยน role / ปิดบัญชีผู้ใช้ / export ข้อมูลส่วนบุคคล
  - 🆕 มีหน้า "บันทึกการใช้งานระบบ" ให้ admin ดูย้อนหลังได้ กรองตาม actor / โครงการ / ช่วงเวลา

### 1.1 บัญชีผู้ใช้ฝั่งเจ้าหน้าที่ 🆕

- **ไม่เปิดให้สมัครเอง** — `admin` เป็นคนสร้างบัญชีหรือส่งคำเชิญทางอีเมล (invite token อายุ 7 วัน ผู้รับตั้งรหัสผ่านเองครั้งแรก)
- `User.passwordHash` เก็บด้วย **argon2id** (หรือ bcrypt cost ≥ 12) ห้ามเก็บ plaintext
- `User.isActive` — admin ปิดบัญชีได้ บัญชีที่ปิดแล้ว login ไม่ได้และถูกตัด session ทันที แต่ยังคงชื่อไว้ใน audit log/`approvedBy` เดิม (ห้ามลบแถวผู้ใช้ทิ้ง)
- มี flow **ลืมรหัสผ่าน** (ส่งลิงก์ reset อายุ 30 นาที ใช้ได้ครั้งเดียว) และ **เปลี่ยนรหัสผ่านเอง**
- บังคับรหัสผ่านอย่างน้อย 12 ตัวอักษร และ rate-limit การ login ต่อบัญชี/ต่อ IP (เช่น 5 ครั้ง/15 นาที)
- **`User.role`**: `organizer` (ค่าเริ่มต้น สร้าง/จัดการโครงการของตัวเองได้) | `admin` (ดูแลระบบ) — ⚠️ ฉบับแรกมี `staff` ด้วยแต่ไม่ได้ใช้งานที่ใดเลย เพราะสิทธิ์หน้างานกำหนดด้วย `EventOrganizer.role = "checkin_only"` รายโครงการอยู่แล้ว จึง**ตัด `staff` ออก** ถ้าต้องการบัญชีที่สร้างโครงการเองไม่ได้ ให้สร้างเป็น `organizer` ที่ไม่มีโครงการของตัวเองแล้วถูกเชิญเข้าโครงการเท่านั้น

### 1.2 โครงการ

- สร้าง/แก้ไข/ลบโครงการอบรม (ชื่อ, รายละเอียด, สถานที่, **วันปิดรับลงทะเบียน**, **โหมดอนุมัติ**, 🆕 **โหมดการนับที่นั่ง**, **ประเภทโครงการ**, **วันที่จัดอบรม**, **รูปปกโครงการ**)
  - ลบโครงการได้เฉพาะ owner เท่านั้น
  - 🆕 **ลบเป็น soft delete เสมอ** (`deletedAt`) ถ้าโครงการมีผู้ลงทะเบียนแล้วอย่างน้อย 1 คน — ห้ามลบข้อมูลจริงทิ้ง เพราะต้องตรวจสอบย้อนหลังได้ และ FK ของ CheckIn/Registrant จะพังตาม โครงการที่ยังไม่มีผู้ลงทะเบียนเลยจะลบจริงก็ได้
- **สถานะโครงการ**: `draft` (ฉบับร่าง ยังไม่เปิดให้ลงทะเบียน กำลังตั้งฟิลด์/รอบ) → `published` (เปิดลิงก์ลงทะเบียนแล้ว) → `closed` (ปิดรับ/จบงานแล้ว)
  - สร้างโครงการใหม่เริ่มเป็น `draft` เสมอ ให้ผู้จัดตั้งฟิลด์ฟอร์ม/วัน/รอบให้ครบ แล้วกดปุ่ม "เผยแพร่" เองเมื่อพร้อม — หน้า public registration page จะขึ้น "ยังไม่เปิดรับลงทะเบียน" ถ้าโครงการยังเป็น draft แม้จะรู้ลิงก์ตรง ๆ
  - เปลี่ยนเป็น `closed` ได้เอง (ไม่ต้องรอ deadline) เช่นกรณีที่นั่งเต็มก่อนกำหนดหรือยกเลิกงาน
  - 🆕 **ลิงก์สาธารณะใช้ `Event.publicSlug`** (สุ่มแบบเดาไม่ได้ เช่น nanoid 12 ตัว) ไม่ใช้ `Event.id` ตรง ๆ เพื่อไม่ให้เดาลิงก์โครงการอื่นจากลิงก์ที่มีอยู่

- 🆕 **กฎการแก้ไขโครงการหลัง `published`** — ต้องบังคับที่ backend:
  - ลดจำนวนที่นั่งให้**ต่ำกว่า** `seatsTaken` ปัจจุบัน → **ห้าม** (แจ้งว่ามีคนจองไปแล้วกี่คน) — โหมด `per_day` เทียบรายวัน, โหมด `whole_course` เทียบที่ `Event.maxSeats` กับจำนวนคนทั้งโครงการ
  - ลบ "วัน" ที่มีผู้เลือกไว้แล้ว → **ห้าม** ต้องยกเลิกรายวันของคนเหล่านั้นก่อน (ระบบช่วยแจ้งเตือนคนที่ได้รับผลกระทบผ่าน broadcast) — 🆕 โหมด `whole_course` ทุกคนผูกอยู่กับทุกวันเสมอ การลบวันจึงกระทบผู้ลงทะเบียนทั้งหมด ต้องยืนยันสองชั้นและบังคับให้ส่ง broadcast แจ้ง
  - ลบ "รอบเช็คชื่อ" ที่มีการเช็คชื่อไปแล้ว → เตือนและต้องยืนยัน (ประวัติเช็คชื่อของรอบนั้นจะหายไปด้วย)
  - เปลี่ยน `eventType` หลังมีผู้ลงทะเบียนแล้ว → เตือนว่าไม่กระทบคนเดิม
  - เพิ่ม "วัน" ใหม่หลัง published → โหมด `per_day` ทำได้ปกติ คนที่ลงทะเบียนไปแล้วไม่ได้ถูกเพิ่มวันให้อัตโนมัติ · 🆕 โหมด `whole_course` ระบบต้องสร้างแถวรายวันของวันใหม่ให้ทุกคนที่ `pending`/`approved` โดยอัตโนมัติ (เพราะนิยามคือ "ต้องมาครบทุกวัน") แล้วเตือนให้ผู้จัดส่ง broadcast
  - 🆕 เปลี่ยน `seatMode` หลังมีผู้ลงทะเบียนแล้ว → **ห้ามเด็ดขาด** ให้ clone เป็นโครงการใหม่แทน

- **Clone โครงการ**: คัดลอกโครงการเดิม (ฟิลด์ฟอร์ม, ประเภท, โหมดอนุมัติ, รอบเช็คชื่อ) มาเป็นโครงการใหม่สถานะ `draft` ได้ทันที เหลือแค่แก้วันที่จัด/ที่นั่ง — ใช้บ่อยเวลาจัดอบรมรุ่นถัดไปที่ฟอร์ม/รูปแบบเดิมเกือบทั้งหมด
  - 🆕 **สิ่งที่คัดลอกมา**: title (เติมคำว่า "(สำเนา)"), description, location, eventType, autoApprove, `seatMode`, `maxSeats`, `attendanceThreshold`, `fields` JSON ทั้งก้อน, รายการรอบเช็คชื่อ (label/เวลา) และรูปปก (คัดลอกไฟล์เป็นสำเนาใหม่ใน object storage ไม่ใช้ URL ร่วมกัน เพราะลบโครงการต้นทางแล้วรูปจะหาย)
  - 🆕 **สิ่งที่ไม่คัดลอก**: ผู้ลงทะเบียนทั้งหมด, ประวัติเช็คชื่อ, ผู้ร่วมจัด (ต้องเชิญใหม่), วันที่จัด + ที่นั่ง (ต้องกรอกใหม่), `registrationDeadline`, `publicSlug` (สุ่มใหม่), สถานะ (เริ่ม `draft` เสมอ)
  - 🆕 รอบที่เดิมผูกกับ `eventDayId` จะถูกคัดลอกมาแบบ **ไม่ผูกวัน** เพราะวันใหม่ยังไม่มี ให้ผู้จัดมาผูกเองในขั้นตอนตั้งรอบ

- **รูปปกโครงการ (cover image)**: อัปโหลดรูปปกได้ 1 รูปต่อโครงการ แสดงบนหน้ารายการโครงการฝั่ง organizer และบนสุดของหน้า public registration page ของโครงการนั้น
  - อัปโหลดผ่าน organizer portal ตอนสร้าง/แก้ไขโครงการ, เปลี่ยนรูปหรือลบรูปทีหลังได้ (ไม่บังคับต้องมี)
  - จำกัดชนิดไฟล์ `jpg/jpeg/png/webp` และขนาดไฟล์สูงสุด (เช่น 5MB) ตรวจสอบทั้งฝั่ง client (UX) และฝั่ง backend (บังคับจริง) — 🆕 ตรวจจาก **magic bytes จริง** ไม่ใช่แค่นามสกุลหรือ `Content-Type` ที่ client ส่งมา
  - Resize/compress อัตโนมัติตอนอัปโหลดเพื่อลดขนาดไฟล์ก่อนเก็บ (เช่นผ่าน sharp) และตั้ง aspect ratio แนะนำ (เช่น 16:9) พร้อม crop preview ให้ผู้จัดเลือกก่อนบันทึก
  - เก็บไฟล์จริงไว้ที่ object storage (เช่น S3-compatible/Cloudflare R2/Vercel Blob) ไม่เก็บเป็น base64 ในฐานข้อมูล — ในตาราง `Event` เก็บแค่ URL
  - 🆕 รูปปกเป็นไฟล์ **สาธารณะได้** (ต่างจากไฟล์แนบของผู้ลงทะเบียน ดูข้อ 1.5) เก็บคนละ prefix/bucket policy กันเพื่อไม่ให้สับสน
- **ประเภทโครงการ**: เลือกได้ 1 ค่าต่อโครงการ
  - **ภายใน (internal)** — ผู้เข้าร่วมเป็นบุคลากร/นักศึกษาภายในหน่วยงาน
  - **ภายนอก (external)** — เปิดรับบุคคลทั่วไปจากภายนอก
  - **ผสม (mixed)** — รับทั้งภายในและภายนอกในโครงการเดียวกัน
- 🆕 **โหมดการนับที่นั่ง (`seatMode`)**: เลือกตอนสร้างโครงการ ล็อกหลัง publish (รายละเอียดเต็มในข้อ 0.1)
  - **แยกรายวัน (`per_day`, ค่าเริ่มต้น)** — "หัวข้อเดียว จัดหลายรอบ เลือกมาวันไหนก็ได้" กำหนดที่นั่งแยกทุกวัน ผู้ลงทะเบียนติ๊กเลือกวันเอง
  - **รวมทั้งคอร์ส (`whole_course`)** — "หลักสูตรต่อเนื่อง ต้องมาครบทุกวัน" กำหนดที่นั่งเป็นตัวเลขเดียวของโครงการ (`Event.maxSeats`) ผู้ลงทะเบียนไม่ต้องเลือกวัน ระบบผูกให้ครบทุกวันเอง — ใช้คู่กับ `attendanceThreshold` (เกณฑ์ % ของรอบที่ต้องเช็คชื่อถึงจะถือว่าผ่านการอบรม) สำหรับออกวุฒิบัตร/รายงาน
  - UI ของหน้าสร้างโครงการต้องเปลี่ยนตามโหมดทันที: โหมด `per_day` ให้กรอกที่นั่งในแต่ละแถววัน, โหมด `whole_course` ให้กรอกที่นั่งช่องเดียวด้านบนแล้วซ่อนช่องที่นั่งรายวันทิ้ง เพื่อไม่ให้ผู้จัดเข้าใจผิดว่ารับ 40 คนต่อวัน
- **วันที่จัดอบรม (หลายวันได้ ไม่จำเป็นต้องต่อเนื่อง)**: ผู้จัดเพิ่ม/ลบ "วัน" ของโครงการเองได้ทีละแถว แต่ละแถวกำหนด
  - วันที่จัดจริง (เช่น จัดวันที่ 1, 5, 6 ของเดือน หรือจัดต่อเนื่องวันที่ 1, 2, 3)
  - **จำนวนที่นั่งรับของวันนั้น ๆ แยกกัน** (เช่น วันที่ 1 รับ 40 คน, วันที่ 5 รับ 60 คน) — แต่ละวันจำกัดจำนวนอิสระจากกัน ไม่ใช้ที่นั่งรวมเดียวกันทั้งโครงการ · 🆕 ช่องนี้ใช้เฉพาะโหมด `per_day`
  - อย่างน้อย 1 วันต่อโครงการ
  - 🆕 ปิดรับเฉพาะบางวันได้ (`EventDay.isClosed`) โดยไม่ต้องปิดทั้งโครงการ — วันที่ปิดจะเลือกไม่ได้ในหน้า public แม้ที่นั่งยังเหลือ (ใช้เฉพาะโหมด `per_day`)
- **โหมดอนุมัติผู้ลงทะเบียน**: มีติ๊ก/toggle ให้เลือกต่อโครงการว่า
  - **อนุมัติอัตโนมัติ (auto-approve)**: ระบบสร้าง QR + ส่งแจ้งเตือนทันทีที่ลงทะเบียนสำเร็จ ไม่ต้องรอผู้จัดกด
  - **อนุมัติเอง (manual, ค่าเริ่มต้น)**: เข้าสถานะ pending รอผู้จัด/ผู้ร่วมจัดกดอนุมัติ/ปฏิเสธตามเดิม
  - เปลี่ยนค่านี้ได้ตลอดระหว่างเปิดรับลงทะเบียน แต่มีผลกับผู้ที่ลงทะเบียน **หลังจากเปลี่ยนค่าเท่านั้น** — ผู้ที่ pending ค้างอยู่ก่อนหน้าไม่ถูกอนุมัติย้อนหลังอัตโนมัติ
- เจ้าของโครงการเพิ่ม/ลบผู้ร่วมจัดคนอื่นได้ (ค้นหาผู้ใช้จากอีเมลแล้วเพิ่มเข้าโครงการ) กำหนดระดับสิทธิ์ได้ 2 แบบต่อคน:
  - **เต็มสิทธิ์ (full)**: แก้ไขฟอร์ม/ดูแดชบอร์ด/อนุมัติผู้ลงทะเบียน/export/เช็คชื่อ ได้เหมือน owner แต่จัดการสิทธิ์คนอื่นหรือลบโครงการไม่ได้
  - **เช็คชื่ออย่างเดียว (check-in only)**: เข้าได้แค่ Check-in App ของโครงการนั้น ไม่เห็นคำตอบฟอร์ม/ข้อมูลส่วนตัวผู้ลงทะเบียนในหน้าอื่น — เหมาะกับเจ้าหน้าที่หน้างานที่ไม่ควรเห็นข้อมูลทั้งหมด
  - 🆕 `checkin_only` เห็นได้เฉพาะฟิลด์ที่ผู้จัดติ๊กไว้ว่า "แสดงบนหน้าจอเช็คชื่อ" (`showOnCheckin: true` ในนิยามฟิลด์) เช่น ชื่อ-นามสกุล กับ หน่วยงาน เท่านั้น ห้ามส่งคำตอบฟิลด์อื่นหรือไฟล์แนบออกจาก API ของ Check-in App เลย (กรองที่ backend ไม่ใช่ซ่อนใน UI)

### 1.3 ป้องกันลงทะเบียนซ้ำ

- เช็คซ้ำในโครงการเดียวกันตอนบันทึก (กันคนกดส่งฟอร์มซ้ำหลายรอบโดยไม่ตั้งใจ) ถ้าซ้ำแจ้งเตือนพร้อมลิงก์ไปหน้าเช็คสถานะของตัวเอง แทนที่จะสร้างแถวใหม่ซ้ำ
- 🆕 **กันซ้ำด้วย `dedupeKey` ไม่ใช่ `email` ตรง ๆ** เพราะ:
  1. คนที่เลือกรับแจ้งเตือนทาง LINE อย่างเดียวจะมี `email = null` ซึ่ง MySQL ปล่อยให้ซ้ำได้ไม่จำกัด → กันซ้ำไม่ได้เลย
  2. คนที่ `cancelled` ไปแล้วอยากกลับมาลงใหม่จะติด unique เข้าระบบไม่ได้อีก

  วิธีแก้: คอลัมน์ `dedupeKey String?` + `@@unique([eventId, dedupeKey])` โดยตั้งค่าเป็น `email` ที่ normalize แล้ว (lowercase, trim) หรือ `line:<lineUserId>` ถ้าไม่มีอีเมล และ **ตั้งเป็น `null` เมื่อสถานะกลายเป็น `cancelled`/`rejected`** เพื่อให้ลงใหม่ได้
- 🆕 normalize อีเมลก่อนเทียบเสมอ (lowercase + trim) ไม่งั้น `A@x.com` กับ `a@x.com` เล็ดลอดเป็นคนละแถว

### 1.4 Dynamic Form Builder

- เพิ่ม/ลบ/เรียงลำดับฟิลด์ลงทะเบียนได้เอง
  - ชนิดฟิลด์ที่ต้องรองรับ: `text`, `textarea`, `email`, `tel`, `date`, `select` (dropdown), `checkbox` (เลือกได้หลายข้อ), `file` (แนบไฟล์ เช่น หนังสือคำสั่งไปราชการ/สำเนาบัตร)
    - `file`: จำกัดชนิดไฟล์ได้ต่อฟิลด์ (เช่น `pdf/jpg/png`) และขนาดสูงสุด (เช่น 5MB) เก็บไฟล์จริงที่ object storage เดียวกับรูปปกโครงการ — ใน `answers` JSON เก็บแค่ **storage key** ของไฟล์ที่อัปโหลดแล้ว (🆕 ไม่ใช่ URL เต็ม ดูข้อ 1.5) ไม่เก็บไฟล์ตรง ๆ ใน JSON
    - ต้อง validate ชนิด/ขนาดไฟล์ซ้ำที่ backend เสมอ (หน้านี้ไม่ login ปลอม request ได้ง่าย เหมือนฟิลด์อื่น) — 🆕 ตรวจจาก magic bytes จริง และตั้ง `Content-Disposition: attachment` ตอนให้ดาวน์โหลด กัน stored XSS จากไฟล์ที่อัปโหลด
  - แต่ละฟิลด์กำหนด `label`, `required` (บังคับ/ไม่บังคับ), `options` (สำหรับ select/checkbox), 🆕 `showOnCheckin` (แสดงบนหน้าจอเช็คชื่อหน้างานหรือไม่), 🆕 `sensitive` (ฟิลด์อ่อนไหว — ปิดบังบางส่วนในตาราง, ไม่ถูก export ถ้าไม่ได้ติ๊กยืนยัน, บันทึก audit เมื่อมีคนเปิดดู)
  - เก็บนิยามฟิลด์เป็น JSON schema ผูกกับแต่ละโครงการ ไม่ hardcode fields ในโค้ด
  - 🆕 **`fields` ต้องมี `key` ที่ไม่เปลี่ยนตลอดอายุโครงการ** (สร้างเป็น nanoid ตอนเพิ่มฟิลด์ ไม่ใช่ slug จาก label) เพราะถ้าผู้จัดแก้ label แล้ว key เปลี่ยนตาม คำตอบเดิมใน `answers` JSON จะหาไม่เจอทั้งหมด
  - **แก้ไข/ลบฟิลด์หลังมีคนตอบแล้ว**: ถ้าฟิลด์นั้นมีคำตอบใน `Registrant.answers` อยู่แล้วอย่างน้อย 1 คน ต้องเตือนผู้จัดก่อนเสมอ (เช่น "มี 12 คนตอบฟิลด์นี้แล้ว ลบจะทำให้ข้อมูลเดิมหลงเหลืออยู่แต่ไม่แสดงในฟอร์มอีก") ห้ามลบเงียบ ๆ — เพราะคำตอบเก่าจะกลายเป็น key กำพร้าที่ค้างอยู่ใน JSON ของคนที่ตอบไปแล้ว ไม่ error แต่ก็ไม่ตรงกับ schema ปัจจุบัน
  - 🆕 **เก็บ `fieldsVersion`** เพิ่มขึ้นทีละ 1 ทุกครั้งที่ schema เปลี่ยน และบันทึก `Registrant.fieldsVersion` ไว้ว่าคนนั้นกรอกตามเวอร์ชันไหน เพื่อให้ตอน export/แสดงผลรู้ว่าคำตอบนี้มาจากฟอร์มหน้าตาแบบใด
  - **ฟิลด์แบบมีเงื่อนไข (conditional fields)**: ฟิลด์ใดก็ได้ตั้งให้ "แสดงเมื่อ" ฟิลด์แม่ (ต้องเป็น `select`/`checkbox` เท่านั้น) ถูกเลือกค่าตรงตามที่กำหนดได้ เช่น เลือก "ประเภทผู้เข้าร่วม = ข้าราชการ" แล้วค่อยโชว์ฟิลด์เพิ่ม "หน่วยงานต้นสังกัด", "ตำแหน่ง", "เลขที่คำสั่งไปราชการ"
    - ตั้งค่าใน builder: toggle "แสดงแบบมีเงื่อนไข" → เลือกฟิลด์แม่ (เฉพาะฟิลด์ type select/checkbox ที่สร้างมาก่อนหน้าฟิลด์นี้) → เลือกค่า (เลือกได้หลายค่า) ที่ทำให้ฟิลด์นี้โผล่
    - เก็บเป็น `conditional: { field, operator: "equals" | "in" | "includes", value }` ต่อฟิลด์ใน JSON schema
    - ฟิลด์ที่ยังไม่โชว์ (เงื่อนไขไม่ตรง) ไม่ถูกบังคับ required แม้ตั้ง required ไว้
    - ลบ/แก้ไขฟิลด์แม่ที่มีฟิลด์ลูกผูกอยู่ → ต้องเตือนผู้จัดก่อนว่ากระทบฟิลด์ลูก
    - 🆕 รองรับความลึกได้ชั้นเดียว (ฟิลด์ลูกเป็นฟิลด์แม่ของอีกฟิลด์ไม่ได้) เพื่อไม่ให้ validation ฝั่ง backend ซับซ้อนเกินจำเป็น — ถ้าจะรองรับหลายชั้น ต้องตรวจ cycle ด้วย

### 1.5 ไฟล์แนบต้องเป็นไฟล์ส่วนตัว 🆕

ฟิลด์ `file` ถูกใช้แนบ "สำเนาบัตรประชาชน / หนังสือคำสั่งไปราชการ" ซึ่งเป็นข้อมูลส่วนบุคคล จึงห้ามเก็บเป็นไฟล์สาธารณะเด็ดขาด:

- bucket/prefix ของไฟล์แนบตั้งเป็น **private** ทั้งหมด (block public access)
- ใน `answers` JSON เก็บแค่ `{ key, originalName, size, mime, uploadedAt }` — **ไม่เก็บ URL** เพราะ URL ที่เก็บไว้ในฐานข้อมูลมักกลายเป็นลิงก์ถาวรที่ใครมีก็เปิดได้
- ตอนผู้จัดกดดู ให้ backend ออก **signed URL อายุสั้น (เช่น 5 นาที)** ทีละครั้ง หลังผ่าน guard สิทธิ์แล้ว
- `checkin_only` เข้าถึงไฟล์แนบไม่ได้ทุกกรณี
- 🆕 บันทึก `AuditLog` ทุกครั้งที่มีการเปิดดู/ดาวน์โหลดไฟล์แนบ (actor, registrantId, fieldKey, เวลา)
- ลบข้อมูลผู้ลงทะเบียน (ตามคำขอที่อนุมัติ) → ต้องลบไฟล์จริงใน storage ด้วย ไม่ใช่ลบแค่แถวในฐานข้อมูล · ไม่มีการลบตามระยะเวลา (เก็บถาวร)

### 1.6 รอบเช็คชื่อ (Session)

- **กำหนดรอบเช็คชื่อของโครงการเอง** เช่น "เช้า", "บ่าย", "วันที่ 1" — เพิ่ม/ลบ/แก้ชื่อรอบได้อิสระ อย่างน้อย 1 รอบต่อโครงการ (สำหรับโครงการหลายวัน ผูกแต่ละรอบกับวันที่จัดวันใดวันหนึ่งได้ เช่น "วันที่ 1 - เช้า", "วันที่ 1 - บ่าย", "วันที่ 5 - เต็มวัน")
- 🆕 รอบที่**ไม่ผูกวัน** (`eventDayId = null`) ใช้เช็คได้ทุกวันของโครงการ และ **ไม่ตรวจ** ว่าคนนั้นเลือกวันไหนไว้ (เหมาะกับกิจกรรมอย่าง "รับของที่ระลึก")
- 🆕 มี `sortOrder` สำหรับจัดลำดับการแสดงผล และ `@@unique([eventId, label])` กันตั้งชื่อรอบซ้ำจนเจ้าหน้าที่หน้างานเลือกผิด
- 🆕 **เตือนตอนเผยแพร่**: ถ้ามี "วัน" ใดที่ไม่มีรอบผูกอยู่เลยและไม่มีรอบแบบไม่ผูกวัน วันนั้นจะเช็คชื่อหน้างานไม่ได้ — ต้องเตือนผู้จัดก่อนกด publish

### 1.7 หน้ารายชื่อ / การอนุมัติ

- **หน้ารายชื่อรออนุมัติ**: แสดงคำตอบของผู้ลงทะเบียนแต่ละคนตามฟิลด์ที่กำหนด พร้อมปุ่ม **อนุมัติ / ปฏิเสธ** เป็นรายคน (และเลือกอนุมัติหลายคนพร้อมกันได้)
  - กดอนุมัติ → ระบบสร้างรหัสลงทะเบียน + QR code แล้วส่งอีเมลตั๋วให้ผู้ลงทะเบียนทันที
  - กดปฏิเสธ → จบ ไม่ได้เข้าร่วม ไม่ได้รับ QR — 🆕 ใส่เหตุผลได้ (ไม่บังคับ) แนบไปในอีเมลแจ้งผล
  - 🆕 แต่ละแถวแสดง**สถานะแยกรายวัน** เป็นชิป เช่น `วันที่ 1 ✓ อนุมัติ` `วันที่ 6 ⏳ คิวที่ 3` และกดอนุมัติ/ปฏิเสธเฉพาะบางวันได้ — 🆕 ในโหมด `whole_course` ให้แสดงเป็นสถานะเดียวของทั้งคน และ**ซ่อนปุ่มรายวันทั้งหมด**
  - 🆕 การอนุมัติแบบหลายคนพร้อมกันต้องทำใน transaction ต่อคนและเช็คที่นั่งทีละวันตามข้อ 0.4 — คนที่วันเต็มระหว่างทางให้ตกเป็น waitlist และสรุปผลให้ผู้จัดเห็นตอนจบว่าใครไม่ผ่านเพราะอะไร
  - **ค้นหา/กรองรายชื่อ**: ค้นหาด้วยชื่อ/อีเมล, กรองตามสถานะ, กรองตามวันที่เลือกเข้าร่วม, กรองตามคำตอบของฟิลด์ใดฟิลด์หนึ่ง (เช่น ดูเฉพาะกลุ่ม "ข้าราชการ") — จำเป็นมากเมื่อมีผู้ลงทะเบียนหลักร้อย/พันคน
  - 🆕 การค้นหาในคอลัมน์ JSON ของ MySQL ช้ามากเมื่อข้อมูลเยอะ ถ้ามีฟิลด์ที่ต้องกรองบ่อย ให้สร้าง **generated column + index** (`ALTER TABLE Registrant ADD COLUMN participant_type VARCHAR(64) AS (answers->>'$.f_xxx') STORED, ADD INDEX ...`) หรือ denormalize ชื่อ-นามสกุลออกมาเป็นคอลัมน์จริง (`displayName`) สำหรับค้นหา
- **เพิ่มผู้ลงทะเบียนเองโดยผู้จัด (manual add)**: สำหรับกรณีมีคนแจ้งชื่อทางโทรศัพท์/walk-in ไม่ได้กรอกผ่านฟอร์มสาธารณะ — กรอกข้อมูลตามฟิลด์เดียวกันแล้วเลือกให้สถานะ approved ได้ทันที (ได้ QR เลย)
  - 🆕 ต้องผ่านการเช็คที่นั่งแบบเดียวกับหน้า public (ข้อ 0.4) และมีตัวเลือก "อนุมัติเกินที่นั่ง (override)" ที่บันทึก audit log ไว้ สำหรับกรณีจำเป็นจริง ๆ
- **ส่ง QR/แจ้งเตือนซ้ำ (resend)**: สำหรับคนที่ approved แล้วแต่อีเมลหาย/หา LINE ไม่เจอ มีปุ่ม "ส่งซ้ำ" ในหน้ารายชื่อ ส่งไปตามช่องทางที่เลือกไว้เดิม
  - 🆕 เปลี่ยนช่องทาง/แก้อีเมลก่อนส่งซ้ำได้ (กรณีกรอกอีเมลผิด) และ rate-limit การส่งซ้ำ (เช่น 3 ครั้ง/ชั่วโมง/คน) กันยิงอีเมลรัว
- **ยกเลิก/ถอนการอนุมัติ (revoke)**: คนที่ approved แล้วแต่แจ้งไม่มาทีหลัง ผู้จัดกด "ยกเลิก" เปลี่ยนสถานะเป็น `cancelled` คืนที่นั่งให้คนอื่น (QR เดิมใช้เช็คชื่อไม่ได้อีก)
  - 🆕 ยกเลิกได้**รายวัน** (เช่น มาได้แค่วันที่ 1 ยกเลิกวันที่ 6) ถ้ายกเลิกครบทุกวันจึงถือว่ายกเลิกทั้งคน และเคลียร์ `qrCode` ทิ้ง — 🆕 โหมด `whole_course` ยกเลิกได้ทั้งคอร์สเท่านั้น
- **Waitlist**: ถ้าที่นั่งของวันที่เลือกเต็มแล้วตอนบันทึก (ทั้ง auto-approve และ manual mode) ให้สถานะของ**วันนั้น**เป็น `waitlisted` แทนที่จะปฏิเสธทั้งคน
  - 🆕 **คิวเรียงตาม `waitlistedAt`** (มี index) แสดงหมายเลขคิวให้ผู้ลงทะเบียนเห็นในหน้าเช็คสถานะ — โหมด `per_day` เป็นคิวของแต่ละวัน ("คิวที่ 3 ของวันที่ 6") · 🆕 โหมด `whole_course` เป็นคิวเดียวของโครงการ ("คิวที่ 3 ของหลักสูตร") เรียงตาม `Registrant.registeredAt`
  - 🆕 **โหมดการเลื่อนคิว ตั้งค่าได้ต่อโครงการ** (`waitlistPromotion`):
    - `auto` — เมื่อมีที่นั่งว่าง ระบบเลื่อนคิวแรกขึ้นเป็น `approved` (หรือ `pending` ถ้าโครงการเป็นโหมด manual) ทันที พร้อมส่งแจ้งเตือน
    - `manual` (ค่าเริ่มต้น) — ระบบแค่แจ้งผู้จัดว่ามีที่นั่งว่าง 1 ที่ในวันที่ X และคิวถัดไปคือใคร ให้ผู้จัดกดเอง
  - 🆕 การเลื่อนคิวต้องทำใน transaction เดียวกับการคืนที่นั่ง เพื่อไม่ให้เลื่อนขึ้นสองคนพร้อมกัน
- **แจ้งเตือนแบบ broadcast**: ส่งข้อความประกาศถึงผู้ลงทะเบียนที่ approved ทั้งหมด (หรือเฉพาะบางวัน) พร้อมกันทางอีเมล/LINE เช่น แจ้งเลื่อนเวลา/เปลี่ยนสถานที่
  - 🆕 เก็บประวัติประกาศไว้ในตาราง `Broadcast` (ใครส่ง, ส่งถึงกลุ่มไหน, เนื้อหา, จำนวนสำเร็จ/ล้มเหลว) ดูย้อนหลังและส่งซ้ำเฉพาะคนที่ส่งไม่สำเร็จได้
  - 🆕 เลือกกลุ่มผู้รับได้มากกว่าแค่ approved: ตามสถานะ (รวม pending/waitlisted), ตามวันที่เลือก, หรือเลือกรายคนที่ติ๊กไว้
- แดชบอร์ด: จำนวนรออนุมัติ / อนุมัติแล้ว / ปฏิเสธ / รอคิว (waitlisted) / ยกเลิก และยอดเช็คชื่อ **แยกตามแต่ละรอบ** (เช่น รอบเช้า 42/60, รอบบ่าย 38/60) แบบ polling refresh ทุก 3-5 วิ
  - 🆕 ตัวหารของแต่ละรอบ = จำนวนคนที่ `approved` **สำหรับวันที่รอบนั้นผูกอยู่** (ไม่ใช่ approved ทั้งโครงการ) รอบที่ไม่ผูกวันให้ใช้ approved ทั้งโครงการ — ต้องเขียนให้ชัดไม่งั้นตัวเลขบนแดชบอร์ดจะชวนเข้าใจผิด · 🆕 โหมด `whole_course` ตัวหารเท่ากันทุกรอบ = จำนวน approved ของโครงการ
  - 🆕 แสดงที่นั่งคงเหลือและจำนวนคิว waitlist ด้วย (รายวันในโหมด `per_day`, ตัวเลขเดียวในโหมด `whole_course`)
  - 🆕 โหมด `whole_course` เพิ่มบล็อก **"ความต่อเนื่องของการเข้าอบรม"**: จำนวนคนที่เข้าครบทุกรอบ / ขาด 1 รอบ / ขาด 2 รอบขึ้นไป และจำนวนคนที่ผ่านเกณฑ์ `attendanceThreshold` — เป็นตัวเลขที่หลักสูตรต่อเนื่องต้องใช้ออกวุฒิบัตรและรายงาน
- Export รายชื่อเป็น CSV (รวมสถานะอนุมัติและสถานะเช็คชื่อแต่ละรอบ)
  - 🆕 รองรับ **.xlsx** ด้วย (หน่วยงานราชการเปิด CSV ภาษาไทยใน Excel แล้วมักเพี้ยน) ถ้าออกเป็น CSV ต้องใส่ **UTF-8 BOM** เสมอ
  - 🆕 ทุกครั้งที่ export ต้องบันทึก `AuditLog` (ใคร, โครงการไหน, กี่แถว, มีฟิลด์ `sensitive` ด้วยหรือไม่) เพราะเป็นการนำข้อมูลส่วนบุคคลออกจากระบบ
  - 🆕 `checkin_only` export ไม่ได้

## 2) PUBLIC REGISTRATION PAGE (ไม่ต้อง login)

- เปิดผ่านลิงก์เฉพาะของแต่ละโครงการ (`/r/<publicSlug>`) — เข้าไม่ได้ถ้าโครงการยังเป็นสถานะ `draft`
- แสดง**รูปปกโครงการ** (ถ้ามี) ไว้บนสุดของหน้า ก่อนรายละเอียดโครงการและฟอร์ม — ถ้าไม่มีรูปปกให้ไม่ต้องแสดงพื้นที่ว่างเปล่า
- **ป้องกันบอท/สแปม**: rate-limit จำนวนครั้งที่ submit ได้ต่อ IP ในช่วงเวลาหนึ่ง เพราะหน้านี้ไม่ login เป็นจุดเสี่ยงที่สุดในระบบ — **ไม่ใช้ CAPTCHA** (ยกเลิก Cloudflare Turnstile แล้ว)
  - 🆕 เพิ่ม honeypot field ที่ซ่อนไว้ และตรวจว่าเวลากรอกฟอร์มสั้นผิดปกติ (< 3 วินาที) เป็นสัญญาณบอท
  - ทุกการตรวจทำที่ **backend** เสมอ (form ticket ที่เซ็นจากเซิร์ฟเวอร์ ไม่เชื่อค่าจากฝั่ง client)
- **PDPA consent**: มี checkbox ยินยอมให้เก็บ/ใช้ข้อมูลส่วนบุคคลตาม พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล บังคับติ๊กก่อน submit ได้ (โดยเฉพาะโครงการที่มีฟิลด์อ่อนไหวอย่างเลขคำสั่งราชการ)
  - 🆕 **ต้องเก็บหลักฐานการยินยอม** ไม่ใช่แค่บังคับติ๊ก: `consentAt`, `consentVersion` (เวอร์ชันข้อความที่ผู้ใช้เห็นตอนนั้น), `consentIp` — และเก็บข้อความ consent แต่ละเวอร์ชันไว้ในระบบ เพื่อย้อนกลับไปดูได้ว่าตอนนั้นยินยอมกับข้อความว่าอะไร
- Render ฟอร์มแบบ dynamic ตาม schema ที่ผู้จัดกำหนดไว้ พร้อม validation ตาม required
  - **ฟิลด์แบบมีเงื่อนไข**: ซ่อนไว้ก่อน โผล่มาแบบ real-time เมื่อค่าฟิลด์แม่ตรงตามเงื่อนไข — ฟิลด์ที่ยังซ่อนอยู่ไม่ต้อง validate required ฝั่ง client
  - **ต้อง validate เงื่อนไขซ้ำที่ backend เสมอ**: เช็คค่าฟิลด์แม่ที่ส่งมาจริงว่าตรงเงื่อนไขไหม ตรงก็บังคับ required ตามกำหนด ไม่ตรงก็เคลียร์ค่าฟิลด์ลูกทิ้งแม้ client จะแอบส่งมาด้วย (กันข้อมูลขยะปนใน `answers` JSON เพราะหน้านี้ไม่ login ปลอมข้อมูลได้ง่าย)
  - 🆕 backend ต้อง **ทิ้ง key ที่ไม่มีอยู่ใน schema ปัจจุบัน** ทั้งหมด (whitelist ตาม `fields`) ไม่ใช่รับทุกอย่างที่ client ส่งมาลง JSON
  - 🆕 จำกัดความยาวค่าต่อฟิลด์ (เช่น text 500 ตัวอักษร, textarea 5,000) และขนาด payload รวม กัน JSON บวมจนฐานข้อมูลอืด
- **การแสดงวันที่จัดอบรมและที่นั่ง ต่างกันตาม `seatMode`** 🆕

  **โหมด `per_day`** — แสดงทุกวันพร้อมที่นั่งคงเหลือของแต่ละวัน (เช่น "วันที่ 1 — เหลือ 12/40 ที่", "วันที่ 5 — เต็มแล้ว", "วันที่ 6 — เหลือ 55/60 ที่")
  - ผู้ลงทะเบียน **เลือกวันที่จะเข้าร่วมได้หลายวันพร้อมกันในการลงทะเบียนครั้งเดียว** ไม่บังคับเลือกแค่วันเดียว
  - วันที่ที่นั่งเต็มแล้วให้ปิดไม่ให้เลือก (disable checkbox) แสดงสถานะ "เต็มแล้ว" ชัดเจน — 🆕 พร้อมตัวเลือก "เข้าคิวรอสำหรับวันนี้" ให้ติ๊กได้ ถ้าเปิดใช้ waitlist
  - ต้องเลือกอย่างน้อย 1 วัน ถึงจะ submit ฟอร์มได้

  **โหมด `whole_course`** 🆕 — แสดงรายการวันทั้งหมดเป็น**ตารางข้อมูลอย่างเดียว ไม่มี checkbox** พร้อมป้ายกำกับชัดเจนว่า "หลักสูตรต่อเนื่อง ต้องเข้าร่วมครบทั้ง N วัน"
  - แสดงที่นั่งคงเหลือเป็นตัวเลขเดียวของหลักสูตร เช่น "เหลือ 12 / 40 ที่นั่ง" — ห้ามแสดงที่นั่งรายวัน จะทำให้เข้าใจผิดว่าลงเฉพาะบางวันได้
  - ถ้ามีเงื่อนไขว่าต้องเข้าร่วมกี่ % ถึงได้วุฒิบัตร (`attendanceThreshold`) ให้แจ้งไว้ในหน้านี้ตั้งแต่ก่อนสมัคร
  - เต็มแล้ว → ปุ่ม submit เปลี่ยนเป็น "เข้าคิวรอ" (ถ้าเปิด waitlist) หรือแสดง "ที่นั่งเต็มแล้ว" แทนฟอร์ม
  - ไม่มีเงื่อนไข "ต้องเลือกอย่างน้อย 1 วัน" เพราะไม่มีให้เลือก
- **ปิดรับลงทะเบียนอัตโนมัติ** เมื่อเลย `registrationDeadline` ของโครงการนั้น — แสดงข้อความแจ้งว่าปิดรับแล้วแทนฟอร์ม (🆕 ตรวจที่ backend ตอน submit ด้วย ไม่ใช่แค่ซ่อนฟอร์ม)
- **ช่องทางรับการแจ้งเตือน**: ให้ผู้ลงทะเบียนเลือกได้ว่าจะรับผลอนุมัติ/QR ทาง **อีเมล** หรือทาง **LINE** — ดูข้อจำกัดสำคัญในข้อ 2.1
- หลังส่งฟอร์ม **โหมด `per_day`** ระบบวนทีละวันที่ผู้ลงทะเบียนเลือก แล้วกำหนดสถานะของวันนั้นตามตาราง (🆕 **โหมด `whole_course`** ตัดสินครั้งเดียวจากที่นั่งรวม แล้วใช้ผลนั้นกับทุกวันพร้อมกัน):

  | ที่นั่งวันนั้น | `autoApprove = false` (ค่าเริ่มต้น) | `autoApprove = true` |
  |---|---|---|
  | ยังเหลือ | `pending` — ยังไม่สร้าง QR ไม่ส่งแจ้งเตือนตั๋ว | `approved` — สร้าง QR + ส่งแจ้งเตือนทันที |
  | เต็มแล้ว | `waitlisted` | `waitlisted` |

  - ข้อความที่แสดงหลัง submit โหมด `per_day` ต้องสรุป**รายวัน** เช่น "ลงทะเบียนสำเร็จ — วันที่ 1 รอการอนุมัติ, วันที่ 6 อยู่ในคิวรอลำดับที่ 3" · 🆕 โหมด `whole_course` สรุปเป็นข้อความเดียว เช่น "ลงทะเบียนสำเร็จ — อยู่ในคิวรอลำดับที่ 3 ของหลักสูตร"
  - QR จะถูกสร้างเมื่อมีวันใดวันหนึ่งกลายเป็น `approved` เป็นครั้งแรก และใช้ใบเดียวกันตลอดทั้งโครงการ
- รหัสลงทะเบียน + QR ที่สร้างขึ้น (ไม่ว่าจะผ่าน manual approve หรือ auto-approve) ใช้ encode รหัสเดียวกันและใช้เช็คชื่อได้ทุกรอบของงาน — **รหัสต้องสุ่มแบบเดาไม่ได้** (UUID v4 หรือ crypto random ≥32 bytes) ห้ามออกเป็นเลขรันตามลำดับหรือรูปแบบที่เดาง่าย เพราะถ้าเดาถูกจะปลอม QR เข้างานได้โดยไม่ผ่านการอนุมัติจริง

### 2.1 ข้อจำกัดของ LINE ที่ต้องตรวจสอบก่อนวางแผน ⚠️🆕

spec เดิมเขียนว่า "ให้ผู้ลงทะเบียน LINE Login แล้วระบบ push QR ไปให้" ซึ่ง **อาจทำไม่ได้ตามที่คิด** — เท่าที่เข้าใจ LINE Messaging API push ข้อความหา `userId` ได้เฉพาะผู้ที่เป็น**เพื่อนกับ Official Account นั้นอยู่แล้ว** และ `userId` ที่ได้จาก LINE Login จะตรงกับฝั่ง Messaging API ก็ต่อเมื่อ LINE Login channel กับ Messaging API channel อยู่ภายใต้ **provider เดียวกัน**

**ต้องไปยืนยันกับเอกสาร LINE Developers ก่อนเริ่มพัฒนาส่วนนี้** เพราะถ้าเป็นจริงจะกระทบ flow หน้าลงทะเบียนโดยตรง แนวทางรองรับ:

- บังคับขั้นตอน "เพิ่มเพื่อน OA" ต่อจาก LINE Login (แสดง QR ของ OA / ปุ่ม add friend) และตรวจสถานะเพื่อนด้วย API ก่อนยืนยันว่าเลือกช่องทาง LINE ได้
- ถ้า push ไม่สำเร็จ ต้อง **fallback** ไปช่องทางสำรองอัตโนมัติ (อีเมล ถ้ามี) และขึ้นเตือนผู้จัดในหน้ารายชื่อว่าคนนี้ส่งไม่ถึง
- ทางเลือกที่ง่ายกว่าและไม่ผูกกับข้อจำกัดนี้: ส่งเป็น **ลิงก์หน้าตั๋วของตัวเอง** (magic link) ทาง SMS หรือแสดงบนหน้าจอให้บันทึกภาพทันทีหลังลงทะเบียน แล้วใช้หน้าเช็คสถานะเป็นช่องทางหลักในการเรียก QR กลับมาดู

### 2.2 หน้าเช็คสถานะ/ดู QR ของฉัน (self-service)

⚠️ **แก้จากฉบับแรก** — เดิมเขียนว่า "กรอกอีเมลหรือรหัสอ้างอิงเพื่อดูสถานะและ QR" ซึ่งหมายความว่าใครก็ตามที่รู้อีเมลของคนอื่น (เดาได้ไม่ยากในหน่วยงานเดียวกัน) จะดึง QR ของคนนั้นไปใช้เข้างานแทนได้ทันที

รูปแบบที่ปลอดภัย:

- กรอกอีเมล/เบอร์ → ระบบ**ส่งลิงก์ชั่วคราว (magic link) หรือ OTP 6 หลัก**ไปยังช่องทางที่ลงทะเบียนไว้ → กดจากลิงก์นั้นจึงเห็นข้อมูล
- ลิงก์/OTP อายุ 15 นาที ใช้ได้ครั้งเดียว ผูกกับ registrant เดียว
- **ตอบกลับแบบเดียวกันเสมอ** ไม่ว่าจะมีอีเมลนั้นในระบบหรือไม่ ("ถ้ามีการลงทะเบียนด้วยอีเมลนี้ ระบบได้ส่งลิงก์ไปแล้ว") กัน enumeration ว่าใครลงทะเบียนไว้บ้าง
- rate-limit การขอลิงก์ (เช่น 3 ครั้ง/15 นาที ต่ออีเมล และต่อ IP)
- รหัสอ้างอิงที่ให้ตอน submit ใช้เข้าได้โดยตรง แต่ต้องยาวและสุ่มพอ (≥ 16 ตัวอักษรจาก crypto random) ไม่ใช่เลขรัน

ในหน้านี้ผู้ลงทะเบียนทำได้:

- ดูสถานะล่าสุด **รายวัน** (pending/approved/waitlisted/rejected/cancelled + หมายเลขคิวถ้าอยู่ใน waitlist)
- ดู/ดาวน์โหลด QR ซ้ำได้เองโดยไม่ต้องรอผู้จัด resend
- **ยกเลิกการเข้าร่วมเอง (self-cancel)** — 🆕 โหมด `per_day` เลือกยกเลิกเฉพาะบางวันได้ คืนที่นั่งให้คิวถัดไปของวันนั้นทันที · โหมด `whole_course` ยกเลิกได้ทั้งหลักสูตรเท่านั้น คืนที่นั่ง 1 ที่ให้คิวแรกของโครงการ
- 🆕 **แก้ไขคำตอบของตัวเอง**ได้ก่อนถึง `registrationDeadline` (เช่น พิมพ์ชื่อผิด) โดยแก้วันที่เลือกได้ด้วยถ้าที่นั่งยังพอ — ทุกการแก้ไขบันทึก audit

## 3) CHECK-IN APP (สำหรับเจ้าหน้าที่หน้างาน, ต้อง login)

- เลือกโครงการที่จะเช็คชื่อ (เห็นเฉพาะโครงการที่ตัวเองมีสิทธิ์ตามกติกาข้อ 1)
- **เลือกรอบเช็คชื่อ (session)** ก่อนเริ่มสแกน/ยิง/ค้นหา (เช่น เลือก "รอบเช้า") — เปลี่ยนรอบได้ตลอดจากหน้าเดียวกัน
  - 🆕 จำรอบที่เลือกไว้ใน localStorage และแสดงชื่อรอบตัวใหญ่ค้างบนหน้าจอตลอดเวลา เพราะเช็คผิดรอบเป็นความผิดพลาดที่พบบ่อยที่สุดหน้างาน
- รองรับ 3 วิธีเช็คชื่อ:
  - **a. สแกนผ่านกล้องมือถือ/เว็บแคม** — ใช้ jsQR หรือ ZXing decode จาก video stream
  - **b. เครื่องยิงบาร์โค้ด/QR แบบ USB หรือ Bluetooth** — ทำงานเป็น keyboard-wedge คือพิมพ์รหัสแล้วส่ง Enter ให้เอง ต้องมี input ที่ auto-focus ตลอดเวลาและ listen `keydown` Enter เพื่อ trigger เช็คชื่อทันที
  - **c. ค้นหาชื่อ/รหัสด้วยมือ** แล้วกดปุ่มเช็คชื่อ
- เช็คชื่อได้เฉพาะผู้ลงทะเบียนที่สถานะ **approved** เท่านั้น (คน pending, waitlisted หรือ rejected เช็คชื่อไม่ได้ ต้องแจ้งเตือนชัดเจนถ้าพยายามสแกน)
- **⚠️ ต้องเช็คว่าคนที่สแกนเลือก "วันนี้" ไว้จริงหรือไม่**: ถ้า session ที่กำลังเช็คอยู่ผูกกับ `eventDayId` ใดวันหนึ่ง ต้องตรวจว่า registrant คนนั้นมีแถวใน `RegistrantEventDay` ของวันนั้น **และแถวนั้นมีสถานะ `approved`** — ถ้าไม่ตรง (เช่น ลงทะเบียนไว้แค่วันที่ 1 แต่มาสแกนวันที่ 6 หรือวันที่ 6 ยังอยู่ในคิวรอ) ต้องเตือนเจ้าหน้าที่ชัดเจนว่า "ไม่ได้ลงทะเบียนวันนี้ไว้" / "วันนี้อยู่ในคิวรอ" ไม่ใช่ปล่อยผ่านอัตโนมัติ
  - 🆕 โหมด `whole_course` ทุกคนมีแถวครบทุกวันอยู่แล้ว กรณี "ไม่ได้ลงวันนี้ไว้" จึงแทบไม่เกิด แต่ยังต้องตรวจตามเดิม (ถ้าเจอแปลว่าข้อมูลเพี้ยน ควรขึ้นเตือนให้ผู้จัดตรวจสอบ)
  - 🆕 มีปุ่ม **"อนุญาตเป็นกรณีพิเศษ"** ให้เจ้าหน้าที่ระดับ full กดผ่านได้ (เช่น ผู้บริหารมาโดยไม่ได้ลงวันนี้) โดยบันทึก `CheckIn.isOverride = true` + เหตุผล ลง audit log — ถ้าไม่มีทางออกนี้ หน้างานจะจบลงด้วยการจดใส่กระดาษแทน
- **กันสแกนซ้ำเฉพาะภายในรอบเดียวกัน**: คนเดิมสแกนซ้ำในรอบที่เลือกอยู่ → แจ้งเตือน "เช็คชื่อรอบนี้ไปแล้ว เมื่อ 09:14" ไม่ error; แต่คนเดิมเช็คชื่อในคนละรอบ (เช่น เช้ากับบ่าย) ต้องทำได้ตามปกติ เพราะนับแยกกัน
- **Feedback หลังสแกนต้องชัดและเร็ว**: แสดงชื่อ + ข้อมูลสำคัญของผู้ลงทะเบียนบนจอทันทีหลังสแกนสำเร็จ พร้อมสี/เสียง beep แยกกรณีชัดเจน — เขียว = เช็คชื่อสำเร็จ, เหลือง = เช็คซ้ำ/ไม่ตรงวัน, แดง = ไม่พบ/ยังไม่ approved
  - 🆕 ข้อมูลที่แสดงต้องเป็นเฉพาะฟิลด์ที่ติ๊ก `showOnCheckin` ไว้ (ดูข้อ 1.2) เพราะจอเช็คชื่อมักหันออกให้คนต่อคิวเห็น
  - 🆕 เสียง beep ต้อง preload ไฟล์เสียงและ unlock AudioContext ด้วยการแตะครั้งแรก (browser บล็อกเสียงอัตโนมัติ) พร้อมสั่น (`navigator.vibrate`) เป็นตัวช่วยในที่เสียงดัง
- **Undo การเช็คชื่อผิดคน**: กดเช็คชื่อผิดคนโดยไม่ตั้งใจ ต้องมีปุ่ม "ยกเลิก" ลบ record เช็คชื่อล่าสุดได้ทันทีจากหน้าเดียวกัน
  - 🆕 **undo = soft delete** (`voidedAt`, `voidedBy`) ไม่ใช่ลบแถวทิ้ง เพื่อให้ตรวจย้อนหลังได้ว่าใครยกเลิกการเช็คชื่อของใครเมื่อไหร่ และให้ `@@unique([registrantId, sessionId])` ยังใช้เช็คซ้ำได้ ให้เปลี่ยนเป็น unique เฉพาะแถวที่ยังไม่ถูก void (ดู schema)
  - 🆕 undo ได้ภายในช่วงเวลาจำกัด (เช่น 10 นาที) สำหรับ `checkin_only` ส่วนสิทธิ์ full ยกเลิกย้อนหลังได้ตลอด
- **ค้นหาด้วยมือรองรับกรณีแก้ไขข้อมูลเล็กน้อยก่อนเช็คชื่อได้** (เช่น กรอกชื่อผิดตอนลงทะเบียน, สแกนไม่ติดเพราะมือถือแบตหมด) ไม่ใช่แค่ค้นแล้วกดเช็คอย่างเดียว
  - 🆕 สิทธิ์ `checkin_only` แก้ได้เฉพาะฟิลด์ที่ `showOnCheckin` เท่านั้น และทุกการแก้บันทึก audit
- อัปเดตสถานะเช็คชื่อของแต่ละรอบให้ทุกอุปกรณ์ที่เปิดหน้านี้อยู่เห็นตรงกัน ผ่านการ poll ข้อมูลใหม่ทุก 3-5 วินาที
  - 🆕 poll แบบ **delta** ส่ง `?since=<timestamp ล่าสุดที่ได้รับ>` และตอบกลับเฉพาะรายการที่เปลี่ยน พร้อมใช้ `ETag`/`If-None-Match` เพื่อให้ตอบ 304 เมื่อไม่มีอะไรเปลี่ยน — ถ้าดึงรายชื่อทั้งหมดทุก 3 วิ × 5 เครื่อง × 1,000 คน จะหนักฐานข้อมูลโดยไม่จำเป็น
- **Resilience ตอนเน็ตหลุดหน้างาน**: ถ้า request เช็คชื่อส่งไม่สำเร็จ ต้อง queue ไว้ใน local (เช่น localStorage/IndexedDB) แล้ว sync อัตโนมัติเมื่อเน็ตกลับมา พร้อมแจ้งเตือนสถานะ "ยังไม่บันทึก รอ sync" ชัดเจน ห้ามทำเหมือนเช็คผ่านแล้วแต่ข้อมูลหายจริง
  - 🆕 ทุกรายการใน queue ต้องมี **`clientEventId` (UUID สร้างที่เครื่อง) + `scannedAt` เวลาจริงที่สแกน** ส่งไปด้วย backend ใช้ `clientEventId` เป็น idempotency key กันบันทึกซ้ำเมื่อ retry และใช้ `scannedAt` เป็นเวลาเช็คชื่อจริงแทนเวลาที่ request มาถึง
  - 🆕 **กติกาเมื่อ sync แล้วชนกัน** ต้องกำหนดให้ชัด:
    - คนนั้นถูกเช็คไปแล้วจากอีกเครื่องในรอบเดียวกัน → ถือว่าสำเร็จ (ไม่สร้างซ้ำ) แจ้งว่า "มีการเช็คจากเครื่องอื่นแล้ว"
    - คนนั้นถูก revoke/ยกเลิกระหว่างที่ออฟไลน์ → **ไม่บันทึก** ขึ้นรายการ "ต้องตรวจสอบ" ให้เจ้าหน้าที่เห็นพร้อมชื่อและเวลา ไม่ใช่เงียบหายไป
    - รอบถูกลบระหว่างนั้น → ไม่บันทึก ขึ้นรายการต้องตรวจสอบเช่นกัน
  - 🆕 เตือนชัดเจนถ้ามีรายการค้างใน queue ตอนผู้ใช้จะปิดหน้าเว็บ (`beforeunload`)
- 🆕 **โหมด `whole_course`: แสดงความต่อเนื่องของคนที่สแกน** — หลังสแกนสำเร็จ ให้โชว์ด้วยว่า "รอบนี้เป็นรอบที่ 4 จาก 8 · เข้าแล้ว 3 รอบ" เพื่อให้เจ้าหน้าที่เตือนคนที่เริ่มขาดได้ตั้งแต่หน้างาน ไม่ต้องรอสรุปตอนจบหลักสูตร
- 🆕 **โหมด kiosk (ไม่บังคับ)**: ตั้งเครื่องแท็บเล็ต/จอให้ผู้เข้าอบรมสแกน QR ของตัวเองเช็คชื่อเอง ลดคิวหน้างาน — ล็อกไม่ให้เห็นรายชื่อคนอื่นและไม่ให้เปลี่ยนรอบโดยไม่ใส่ PIN

```prisma
model Registrant {
  id            String    @id @default(cuid())

  event         Event     @relation(fields: [eventId], references: [id], onDelete: Cascade)

  fieldsVersion Int       @default(1) // กรอกตามฟอร์มเวอร์ชันไหน

  registeredAt  DateTime  @default(now())
  updatedAt     DateTime  @updatedAt

  email         String?
  lineUserId    String?

  // whole_course: เป็นสถานะจริงของทั้งคน และทุกแถว RegistrantEventDay ต้องมีค่าตรงกับตัวนี้เสมอ

  consentAt      DateTime?
  consentVersion String?
  consentIp      String?

  checkIns      CheckIn[]
  days          RegistrantEventDay[]
  notifications NotificationLog[]

  @@unique([eventId, dedupeKey]) // กันลงซ้ำ รองรับทั้งคนที่ใช้ LINE และคนที่ยกเลิกแล้วลงใหม่
  @@index([eventId, status])
  @@index([eventId, displayName])
}

// ---------- ⭐ หัวใจของระบบ: สถานะอนุมัติรายวัน ----------
model RegistrantEventDay {

  registrant   Registrant @relation(fields: [registrantId], references: [id], onDelete: Cascade)

  cancelledBy  String?

  @@index([eventDayId, status])              // นับที่นั่งที่ถูกจองของวันนั้น
  @@index([eventDayId, status, waitlistedAt]) // ดึงคิวถัดไป

// ---------- เช็คชื่อ ----------
model CheckIn {
  id            String     @id @default(cuid())
  registrantId  String
  registrant    Registrant @relation(fields: [registrantId], references: [id], onDelete: Cascade)
  sessionId     String
  session       Session    @relation(fields: [sessionId], references: [id], onDelete: Cascade)
  checkedInAt   DateTime   @default(now()) // เวลาที่สแกนจริง (จาก scannedAt ของ client ถ้ามาจาก offline queue)
  checkedInBy   String?
  method        String     @default("camera") // camera | scanner | manual | kiosk
  isOverride    Boolean    @default(false)    // กดอนุญาตพิเศษทั้งที่ไม่ตรงวัน
  overrideNote  String?
  clientEventId String?    @unique            // idempotency key จาก offline queue
  syncedAt      DateTime?                     // เวลาที่ sync เข้าระบบจริง (ต่างจาก checkedInAt ได้)

  // undo = soft delete ห้ามลบแถวทิ้ง
  voidedAt      DateTime?
  voidedBy      String?
  voidReason    String?
  isActive      Boolean    @default(true)     // ตั้งเป็น false เมื่อ void — ใช้คู่กับ unique ด้านล่าง

  @@unique([registrantId, sessionId, isActive]) // กันเช็คซ้ำเฉพาะแถวที่ยัง active
  @@index([sessionId, checkedInAt])
}
```

> ⚠️ หมายเหตุเรื่อง `@@unique([registrantId, sessionId, isActive])`: MySQL ถือว่า `false` เป็นค่าหนึ่ง ไม่ใช่ null จึงยัง void ซ้ำสองครั้งไม่ได้ ถ้าต้องการ void ได้หลายครั้งจริง ๆ ให้เปลี่ยน `isActive` เป็น `activeKey String?` ที่ตั้งค่าเป็น `sessionId` เมื่อ active และ `null` เมื่อ void แล้วทำ `@@unique([registrantId, activeKey])` แทน (MySQL ปล่อยให้ null ซ้ำได้)

### 🆕 หมายเหตุสำคัญเรื่อง schema

- **ทุกตารางมี `onDelete` ชัดเจน** — ฉบับแรกไม่มีเลย ซึ่งจะทำให้ลบ event ไม่ได้เพราะติด FK constraint
- **`updatedAt` ในตารางหลัก** ใช้ทำ delta polling (`?since=`) และตรวจ conflict ตอนแก้พร้อมกัน
- **index ที่จำเป็นต่อ performance**: `RegistrantEventDay(eventDayId, status)` สำหรับนับที่นั่ง (query ที่ถูกเรียกบ่อยที่สุดในระบบ), `Registrant(eventId, status)` สำหรับหน้ารายชื่อ, `CheckIn(sessionId, checkedInAt)` สำหรับแดชบอร์ดและ delta poll
- 🆕 **โหมด `whole_course` นับที่นั่งจากตาราง `Registrant`** (`@@index([eventId, status])` ที่มีอยู่แล้วครอบคลุม) ไม่ใช่จาก `RegistrantEventDay` — แถวรายวันในโหมดนี้มีไว้ให้ Check-in App และรายงานรายวันใช้ ไม่ได้มีไว้นับที่นั่ง
- ถ้าจะกรองตามคำตอบใน `answers` JSON บ่อย ๆ ให้เพิ่ม **generated column + index** ตามข้อ 1.7 อย่าพึ่ง `JSON_EXTRACT` แบบ full scan

## ACCESS CONTROL

ต้อง enforce ที่ backend/API ทุก endpoint ไม่ใช่แค่ซ่อนใน UI:

- รายการโครงการ, แก้ไขฟอร์ม, ดูแดชบอร์ด, อนุมัติ/ปฏิเสธผู้ลงทะเบียน, export CSV, เข้าหน้าเช็คชื่อ: ต้องเป็น owner หรือมีแถวใน `EventOrganizer` ของโครงการนั้นเท่านั้นถึงเข้าถึงได้
  - ถ้า `EventOrganizer.role = "checkin_only"` เข้าได้แค่ endpoint ของ Check-in App เท่านั้น endpoint อื่น (ฟอร์ม, คำตอบผู้ลงทะเบียน, dashboard, export, ไฟล์แนบ) ต้อง reject แม้จะอยู่ในโครงการเดียวกัน
  - 🆕 API ของ Check-in App ต้อง **กรองฟิลด์ที่ส่งออก** ให้เหลือเฉพาะ `showOnCheckin` ก่อน serialize ไม่ใช่ส่งทั้งก้อนแล้วซ่อนใน UI
- ลบโครงการ / เพิ่ม-ลบผู้ร่วมจัด / เปลี่ยนสถานะโครงการ (publish/close): เฉพาะ owner เท่านั้น
- ต้องมี middleware/guard ตรวจสิทธิ์นี้ทุกครั้งที่ request เข้าถึงข้อมูลของ event ใด ๆ
- 🆕 เขียน guard เป็น **ฟังก์ชันกลางตัวเดียว** `requireEventAccess(userId, eventId, need: "owner" | "full" | "checkin")` คืน context ที่บอกสิทธิ์ ใช้ซ้ำได้ทั้งใน server component และ route handler — และให้มัน **บันทึก audit เองอัตโนมัติ** เมื่อผู้เข้าถึงเป็น admin ที่ไม่ได้อยู่ในโครงการ
- 🆕 endpoint สาธารณะ (หน้าลงทะเบียน, หน้าเช็คสถานะ, upload ไฟล์แนบ) ต้อง rate-limit ทุกตัว และ **อ้างอิงโครงการด้วย `publicSlug` เท่านั้น** ห้ามรับ `eventId` ตรง ๆ จาก client
- 🆕 ตั้ง security headers ครบ (CSP, X-Content-Type-Options, Referrer-Policy, HSTS), cookie เป็น `HttpOnly; Secure; SameSite=Lax`, และเปิด CSRF protection สำหรับทุก mutation ที่ใช้ cookie

## 🆕 PDPA / การเก็บและลบข้อมูล

ระบบนี้เก็บข้อมูลส่วนบุคคลของบุคคลภายนอก (ชื่อ-สกุล เบอร์โทร อีเมล หน่วยงาน และอาจมีสำเนาบัตร/เลขคำสั่งราชการ) จึงต้องระบุไว้ตั้งแต่ออกแบบ:

- **วัตถุประสงค์** — ระบุในข้อความ consent ว่าใช้เพื่อจัดอบรม ตรวจสอบการเข้าร่วม และออกวุฒิบัตรเท่านั้น
- **ระยะเวลาเก็บ** — 🆕 (แก้ 16 ต.ค. 2026) **เก็บข้อมูลที่ลงทะเบียนและไฟล์แนบไว้ถาวร ไม่มีการลบ/ปกปิดอัตโนมัติตามระยะเวลา** (ยกเลิกการตั้งระยะเก็บต่อโครงการและ scheduled job anonymize เดิม) · ข้อมูลของผู้ลงทะเบียนรายบุคคลถูกปกปิดได้ทางเดียวคือคำขอลบข้อมูลของเจ้าของข้อมูลที่ผู้จัดอนุมัติ (ดู "สิทธิ์เจ้าของข้อมูล") · ประกาศความเป็นส่วนตัวต้องระบุระยะเวลาเก็บให้ตรงกับข้อนี้
- **สิทธิ์เจ้าของข้อมูล** — มีช่องทางขอเข้าถึง/แก้ไข/ลบข้อมูลของตัวเอง (ใช้หน้าเช็คสถานะเป็นช่องทางหลัก) และบันทึกทุกคำขอ
- **บันทึกการเข้าถึง** — ดูไฟล์แนบ, export, และ admin เข้าโครงการคนอื่น ต้องลง `AuditLog` ทุกครั้ง
- **ผู้ประมวลผลข้อมูล** — ถ้าใช้บริการภายนอก (Resend, LINE, ผู้ให้บริการ object storage) ควรระบุไว้ในประกาศความเป็นส่วนตัว
- **ห้ามใส่ข้อมูลส่วนบุคคลใน log ของระบบ** (อีเมล/ชื่อ/เลขบัตร) ให้ log เป็น id แทน

## TECH STACK ที่ต้องการ

- **Frontend**: Next.js (App Router) + TypeScript + **shadcn/ui** (Radix UI primitives + Tailwind CSS ใต้ฮู้ด, ใช้ CLI ของ shadcn เพิ่มคอมโพเนนต์ทีละตัว เช่น form, table, dialog, badge)

- **Realtime**: polling ทุก 3-5 วินาทีบนหน้าแดชบอร์ด, หน้ารออนุมัติ, และหน้าเช็คชื่อ (ไม่ใช้ Socket.io เพื่อลดความซับซ้อน) — 🆕 ใช้ delta + ETag ตามข้อ 3
- **Auth (ฝั่ง organizer/staff)**: NextAuth.js (Credentials provider) — 🆕 argon2id สำหรับ hash รหัสผ่าน, session แบบ database ไม่ใช่ JWT อย่างเดียว เพื่อให้ตัด session ของบัญชีที่ถูกปิดได้ทันที
- **LINE Login (ฝั่งผู้ลงทะเบียน)**: LINE Login เพื่อรับ `lineUserId` + **LINE Messaging API** สำหรับ push — ⚠️ ดูข้อจำกัดในข้อ 2.1 ก่อนวางแผน
- **QR generation**: `qrcode` (npm) — สร้างตอนอนุมัติเท่านั้น โดย encode รหัสจาก `crypto.randomUUID()` หรือ `crypto.randomBytes(32)` (ห้ามใช้ ID ที่รันตามลำดับ) — แก้ 7 ต.ค. 2026: รหัสรูปแบบ `RPP-XXXX-XXXX` เช่น `RPP-7Q2M-4KX9` (สุ่ม 8 ตัวด้วย `crypto.randomInt` จากตัวพิมพ์ใหญ่และตัวเลข ไม่ใช้ 0/O/1/I · ตรวจไม่ให้ซ้ำในฐานก่อนออก · หน้าเช็คชื่อรับรหัสที่พิมพ์ตัวเล็กได้) · รหัสที่ออกก่อนแก้ยังใช้เช็คชื่อได้ตามเดิม
- **QR scanning (กล้อง)**: `jsQR` หรือ `@zxing/browser`
- **Email**: Resend หรือ Nodemailer + SMTP — 🆕 ส่งผ่าน **background job/queue** (เช่น BullMQ + Redis หรือ cron table ในฐานข้อมูล) ไม่ใช่ส่งตรงใน request handler เพราะ broadcast หลักพันฉบับจะทำให้ request timeout และต้อง retry ได้
- **Hosting**: Vercel หรือ VPS ธรรมดา (frontend) + PlanetScale / Railway / VPS ที่มี MySQL — 🆕 ถ้าใช้ Vercel serverless ต้องระวังเรื่อง connection pool ของ Prisma (ใช้ Prisma Accelerate หรือ pgbouncer-equivalent) และ job แบบ cron ต้องใช้ Vercel Cron
- **Export**: `papaparse` (CSV + BOM) และ 🆕 `exceljs` สำหรับ .xlsx
- **Image upload/storage**: object storage (S3-compatible / Cloudflare R2 / Vercel Blob) + `sharp` — 🆕 bucket ของไฟล์แนบต้อง private + signed URL ตามข้อ 1.5
- **Bot protection**: honeypot + ตรวจเวลากรอกฟอร์ม + rate-limit ต่อ IP บนหน้า public registration page (ไม่ใช้ CAPTCHA)
- 🆕 **PDF** (วุฒิบัตร/รายงาน): `@react-pdf/renderer` หรือ Playwright render HTML → PDF
- 🆕 **Validation**: `zod` สร้าง schema แบบ dynamic จาก `fields` JSON แล้วใช้ตัวเดียวกันทั้ง client และ server กันกฎสองชุดไม่ตรงกัน

## ข้อกำหนดเพิ่มเติม

- Mobile-responsive ทุกหน้า โดยเฉพาะหน้าเช็คชื่อหน้างานที่ต้องใช้งานบนมือถือ/แท็บเล็ตได้ดี
- หน้าเช็คชื่อต้องรองรับทั้งอินพุตจากกล้องและจากเครื่องยิงบาร์โค้ดพร้อมกันในหน้าเดียว
- ระบบต้องรองรับหลายโครงการพร้อมกัน แต่ละโครงการมีฟิลด์ลงทะเบียนและรอบเช็คชื่อต่างกันได้อิสระ
- ป้องกัน SQL injection / validate input ทุกจุดที่รับข้อมูลจากผู้ใช้ภายนอก (หน้าลงทะเบียนสาธารณะเป็นจุดเสี่ยงที่สุด เพราะไม่ต้อง login)
- 🆕 **สถานะ UI ครบทุกหน้า**: loading, empty, error, ไม่มีสิทธิ์ (403), ไม่พบ (404), เกิน rate limit (429) — ฉบับแรกออกแบบไว้แต่ทางสำเร็จ
- 🆕 **หน้า login / ลืมรหัสผ่าน / ตั้งรหัสผ่านครั้งแรก** ยังไม่มีใน spec เดิม ต้องมี
- 🆕 **เสียง beep + การสั่น** ต้องเตรียมไฟล์และ unlock audio ตามข้อ 3
- 🆕 **Accessibility ขั้นต่ำ**: label ผูกกับ input ทุกช่อง, โฟกัสมองเห็นได้, contrast ผ่าน WCAG AA, ใช้คีย์บอร์ดได้ทั้งหมด (สำคัญเพราะเครื่องยิงบาร์โค้ดทำงานผ่านคีย์บอร์ด)
- 🆕 **Seed data + ข้อมูลทดสอบ**: สคริปต์สร้างโครงการตัวอย่าง **สองโครงการ — โหมด `per_day` 3 วัน 4 รอบ และโหมด `whole_course` 5 วัน 10 รอบ** ผู้ลงทะเบียน 200 คนสถานะคละกัน เพื่อทดสอบ performance ของหน้ารายชื่อและแดชบอร์ดตั้งแต่เนิ่น ๆ
- 🆕 **การทดสอบที่ต้องมีอย่างน้อย**: unit test ของ logic คำนวณที่นั่ง/waitlist **ทั้งสองโหมด**, integration test ของการจองที่นั่งแบบ concurrent (ยิงพร้อมกัน 50 request ต้องไม่เกิน maxSeats ของโหมดนั้น), และ test ของ guard สิทธิ์ทุกระดับ
- 🆕 **Operations**: health check endpoint, โครงสร้าง log ที่ไม่มีข้อมูลส่วนบุคคล, แผนสำรองข้อมูล MySQL + object storage, และรายการ env ที่ต้องตั้งครบ (`DATABASE_URL`, `NEXTAUTH_SECRET`, LINE channel id/secret/token, SMTP/Resend key, S3 credentials, `APP_BASE_URL`)

## Flow การทำงานโดยสรุป

**ผู้จัด (ตั้งค่าก่อนเปิดลงทะเบียน):** สร้างโครงการ สถานะเริ่มเป็น `draft` (ระบุประเภทภายใน/ภายนอก/ผสม + วันปิดรับลงทะเบียน + เลือกโหมดอนุมัติ auto/manual + โหมดเลื่อนคิว waitlist + **เลือกโหมดการนับที่นั่ง: แยกรายวัน หรือ รวมทั้งคอร์ส**) → เพิ่มวันที่จัดอบรม (วันเดียวหรือหลายวัน ไม่ต้องต่อเนื่อง) พร้อมกำหนดที่นั่ง — แยกรายแถววัน (โหมด `per_day`) หรือกรอกตัวเลขเดียวของหลักสูตร (โหมด `whole_course`) → กำหนดฟิลด์ลงทะเบียน (ติ๊กว่าฟิลด์ไหนแสดงหน้าจอเช็คชื่อ / ฟิลด์ไหนอ่อนไหว) → กำหนดรอบเช็คชื่อ (เช้า/บ่าย ฯลฯ ผูกกับวันใดวันหนึ่งได้) → เพิ่มผู้ร่วมจัด (เต็มสิทธิ์ หรือเช็คชื่ออย่างเดียว) → ระบบตรวจว่าทุกวันมีรอบผูกอยู่ → กด **เผยแพร่ (publish)**

**ผู้เข้าอบรม (ลงทะเบียน) — โหมด `per_day`:** เห็นรายการวันที่จัด + ที่นั่งคงเหลือของแต่ละวัน → เลือกวันที่จะเข้าร่วม (เลือกได้หลายวันพร้อมกัน) → กรอกฟอร์ม เลือกช่องทางรับแจ้งเตือน → ติ๊กยินยอม PDPA (ระบบเก็บหลักฐาน) → submit (ผ่านการตรวจกันบอท, ปิดอัตโนมัติเมื่อเลย deadline) → **ระบบตัดสินสถานะแยกทีละวัน** ตามตารางในข้อ 2:
  - วันที่ยังมีที่นั่ง + โหมด manual → วันนั้น `pending`
  - วันที่ยังมีที่นั่ง + โหมด auto → วันนั้น `approved` ได้ QR ทันที
  - วันที่เต็มแล้ว → วันนั้น `waitlisted` พร้อมหมายเลขคิว
  - กลับมาเช็คสถานะ/ดู QR ซ้ำ แก้ข้อมูล หรือยกเลิกเฉพาะบางวันได้ทุกเมื่อผ่านหน้าเช็คสถานะ (ต้องยืนยันตัวตนผ่าน magic link/OTP ก่อน)

**ผู้เข้าอบรม (ลงทะเบียน) — โหมด `whole_course`:** 🆕 เห็นตารางวันทั้งหมดของหลักสูตรพร้อมข้อความว่าต้องเข้าร่วมครบทุกวัน + ที่นั่งคงเหลือตัวเลขเดียว → ไม่ต้องเลือกวัน → กรอกฟอร์ม เลือกช่องทางรับแจ้งเตือน → ติ๊กยินยอม PDPA → submit → ระบบตัดสินครั้งเดียวจากที่นั่งรวม แล้วสร้างแถวรายวันให้ครบทุกวันด้วยสถานะเดียวกัน (`pending` / `approved` / `waitlisted` พร้อมเลขคิวของหลักสูตร)

**ผู้จัด (อนุมัติ, เฉพาะโครงการโหมด manual):** ตรวจคำตอบรายคน (ค้นหา/กรองได้) → อนุมัติ/ปฏิเสธ ทั้งคนหรือเฉพาะบางวัน (เฉพาะโหมด `per_day`; โหมด `whole_course` อนุมัติเป็นก้อนเท่านั้น) โดยระบบเช็คที่นั่งอีกครั้งตอนกด ถ้าเต็มระหว่างทางจะตกเป็น waitlist และแจ้งให้เห็น → เพิ่มคนเองแบบ manual ได้, ส่ง QR ซ้ำได้, ยกเลิกรายวันได้ (คืนที่นั่งให้คิว waitlist ของวันนั้น), ส่งประกาศ broadcast พร้อมดูประวัติการส่งได้

**ผู้เข้าอบรม:** ได้รับ QR ทางอีเมลหรือ LINE หลังอนุมัติ ใช้ QR เดียวกันเช็คชื่อได้ทุกรอบที่ตัวเองได้รับอนุมัติ

**เจ้าหน้าที่หน้างาน (วันงานจริง):** เลือกโครงการ → เลือกรอบที่จะเช็ค → เช็คชื่อด้วยกล้อง/เครื่องยิง/ค้นหา (ต้อง `approved` **ของวันที่รอบนั้นผูกอยู่**) → เช็คซ้ำในรอบเดียวกันถูกกัน แต่คนละรอบเช็คได้อีก → เห็น feedback สี/เสียงชัดเจนทันที undo ได้ถ้าพลาด (soft delete) → กรณีพิเศษกดอนุญาตผ่านได้พร้อมบันทึกเหตุผล → สถานะอัปเดตทุกเครื่องผ่าน delta poll แม้เน็ตหลุดก็ queue ไว้ sync ทีหลังพร้อมกติกาจัดการรายการที่ชนกัน

**ผู้จัด (ระหว่างงาน):** ดูแดชบอร์ดยอดรออนุมัติ/อนุมัติแล้ว/ปฏิเสธ/รอคิว/ยกเลิก ที่นั่งคงเหลือ และยอดเช็คชื่อแยกตามแต่ละรอบ (ตัวหาร = คนที่ approved ของวันที่รอบนั้นผูกอยู่ · โหมด `whole_course` = approved ทั้งโครงการ พร้อมบล็อกสรุปคนที่เข้าครบ/ขาด/ผ่านเกณฑ์)

## ลำดับการพัฒนาที่แนะนำ

เริ่มจากด้านที่ "ของอื่นต้องพึ่งพา" ไปหาด้านที่ "พึ่งพาของอื่น" — แต่ละขั้นทดสอบจบเป็นระยะได้

1. **Setup โปรเจกต์ + วาง Prisma schema ทั้งหมดให้จบก่อน** — Next.js (App Router) + TS + shadcn/ui, ต่อ MySQL, ตั้ง `.env` ใส่ทุก model ที่คุยกันไว้ทีเดียว **รวม `RegistrantEventDay.status`, `AuditLog`, `NotificationLog`, `Broadcast` ตั้งแต่รอบแรก** เพราะ field/relation กระทบทุกหน้าที่จะสร้างทีหลัง แก้ทีหลังจะย้อนแก้เยอะกว่ามาก
2. **Auth (NextAuth Credentials) + access control guard** — 🆕 รวมหน้า login/ลืมรหัสผ่าน/ตั้งรหัสครั้งแรก และเขียน guard function กลาง (`requireEventAccess`) ที่บันทึก audit เองได้ ใช้ซ้ำทั้ง server component และ API route
3. **CRUD โครงการพื้นฐาน (ยังไม่ต้องมี form builder)** — สร้าง/แก้ไข/soft delete, สถานะ draft/published/closed + กฎห้ามแก้ที่กระทบคนที่ลงแล้ว, วันที่จัดหลายวัน + **ทั้งสองโหมดการนับที่นั่ง (`per_day` / `whole_course`) ตั้งแต่รอบแรก** เพราะ UI หน้าสร้างโครงการและตรรกะที่นั่งแตกกันตั้งแต่ตรงนี้, ประเภทโครงการ, รูปปก, `publicSlug`
4. **🆕 Logic ที่นั่ง + waitlist เป็นโมดูลแยก พร้อม test** — เขียน `getSeatAvailability()` / `reserveSeats()` / `promoteFromWaitlist()` / `releaseSeat()` เป็นฟังก์ชันกลางที่**แตกตาม `seatMode` ภายในตัวมันเอง** พร้อม concurrent test ทั้งสองโหมด (ยิงพร้อมกัน 50 request: โหมด per_day ต้องไม่เกิน maxSeats ของแต่ละวัน, โหมด whole_course ต้องไม่เกิน `Event.maxSeats` และคน 1 คนต้องไม่ถูกนับเป็นหลายที่นั่ง) ก่อนเอาไปใช้ในหน้า public, manual add และหน้าอนุมัติ — เพราะทั้งสามทางเรียกตรรกะเดียวกัน ถ้าเขียนแยกกันสามที่จะไม่ตรงกันแน่นอน
5. **Dynamic Form Builder + Conditional Fields** — ต้องมี event จริงให้ผูก JSON schema ของฟิลด์เข้าไป รวมฟิลด์ `file` upload (private + signed URL) และ zod schema แบบ dynamic ใช้ร่วมกันสองฝั่ง
6. **Public Registration Page** — ต้องมี form schema จริงถึงจะ render ฟอร์ม dynamic ได้ รวมการกันบอท (honeypot + rate-limit), PDPA consent + หลักฐาน, เลือกวันหลายวัน, เรียก `reserveSeats()` จากขั้นที่ 4
7. **หน้าเช็คสถานะ self-service (magic link/OTP)** — 🆕 ยกขึ้นมาก่อนหน้าอนุมัติ เพราะเป็นช่องทางที่ผู้ลงทะเบียนใช้แทน resend และลดภาระผู้จัดตั้งแต่วันแรก
8. **หน้าอนุมัติ + แดชบอร์ด + แจ้งเตือน (Email/LINE ผ่าน queue) + Export CSV/xlsx** — ต้องมี registrant จริงจากขั้นก่อนหน้ามาทดสอบ approve/reject รายวัน/waitlist/revoke/resend/broadcast
9. **Check-in App (กล้อง/เครื่องยิง/ค้นหา)** — ทำท้ายสุดเพราะต้องมีคน `approved` จริงมาทดสอบ รวม logic เช็ควันที่ตรง, กันสแกนซ้ำ, override, undo แบบ soft delete, delta poll, offline queue + กติกา conflict
10. **🆕 หน้า admin + audit log viewer** — ทำได้หลังจากมีข้อมูล audit สะสมจากขั้น 2-9 แล้ว
11. **🆕 เฟส 2** — วุฒิบัตร, รายงานสรุป, reminder ก่อนวันงาน, แบบประเมิน, kiosk
